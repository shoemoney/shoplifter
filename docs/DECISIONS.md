# Architecture Decisions

Records choices the PRD left open, and every deviation from it. Each entry states the smallest
reversible option taken, so a later milestone can revisit it cheaply.

## M0-1 — Balance and atlas data validate with Zod, not raw JSON Schema

The PRD allows either. Zod gives the parsed TypeScript type and the validator from one
declaration, so `Balance` cannot drift from `balance.json`. Cost: ~12 kB gzipped in the bundle.
Revisit if the bundle budget tightens; the loaders are the only call sites.

## M0-2 — `src/render/webgpu/textures.ts` is a module the PRD tree does not list

The PRD module tree names `context`, `deviceRecovery`, `pipelines`, `spriteBatch`, `particles`,
`lighting`, `post` and `shaders/`. Atlas decode and upload belongs to none of them, and putting
it in `context.ts` would mix device acquisition with asset IO. Added as a sibling.

## M0-3 — GPU resources are registered as factories, not created directly

`RenderHost.register()` takes a `build(context)` closure and rebuilds every registered resource
after device loss. This is heavier than calling `device.createBuffer` inline, and it is the only
way to satisfy the PRD's requirement to "preserve CPU copies or reload descriptors for all GPU
resources needed after device loss" without a per-resource rescue path.

## M0-4 — One sprite pipeline with premultiplied alpha, one atlas, one draw call

Instances are 64 bytes (16 floats, two of them padding) so every instance is 16-byte aligned.
Additive effects will reuse the same pipeline by authoring premultiplied art rather than adding
a second blend state, which would force a pipeline switch mid-frame and split the batch.
Revisit at Milestone 2 if particles genuinely need a distinct blend mode.

## M0-5 — Depth is a per-instance value in `[0, 1]`, with no depth buffer yet

Parallax layers order by writing `depth` into clip-space Z. There is no depth attachment in
Milestone 0 because nothing needs occlusion yet; the field exists so adding one later does not
change the instance layout. Draw order still decides overlap.

## M0-6 — `Math.random()` is banned by ESLint, not by convention

`no-restricted-properties` on `Math.random` fails the build. Determinism is load-bearing for
replay verification and for the gameplay acceptance tests, and a single stray call is invisible
in review.

## M0-7 — The clock drops ticks past `maxTicksPerFrame` (8) rather than catching up

A one-second stall queues 120 ticks at 120 Hz; simulating them takes longer than real time and
the app never recovers. Dropping is visible (the overlay counts it) and bounded. Simulation time
is therefore not wall-clock time after a stall, which is correct for gameplay and must be
accounted for in any wall-clock mission timer.

## M0-8 — Float remainder means the tick count can trail exact by one tick

`advance(1/144)` a thousand times does not sum to an exact number of 1/120 s ticks in float64.
The accumulator carries the remainder, so error never grows past one tick — but a test asserting
an exact tick count for a non-integer frame rate is wrong, not the clock. `clock.test.ts`
asserts the bound, not an exact figure.

## M0-9 — The placeholder atlas is generated by a committed Python script

`tools/make_placeholder_atlas.py` writes `public/assets/atlas.png` (823 bytes). Art direction is
still an open PRD decision, and a generator keeps binary churn out of history while art is
provisional. CI regenerates it and fails on a diff, so the script and the committed PNG cannot
drift apart.

## M0-10 — Asset load failure substitutes a magenta checker, not an empty texture

An invisible placeholder reads as a broken draw call and costs debugging hours. The overlay also
reports `assets: PLACEHOLDER` and the e2e suite asserts `placeholderAssets === false`, so a
missing atlas fails CI rather than shipping quietly.

## M0-11 — `GameApp.stepDemo` is placeholder kinematics, deliberately not the flight model

Milestone 0 needs a moving sprite to prove interpolation and input. Implementing the real flight
model here would mean writing it before its own tests exist. Milestone 1 deletes `stepDemo`.

## M0-12 — Pause resets the frame timer instead of gating the accumulator

Resuming from pause must not deliver the paused wall-clock time to the simulation. The minimal
fix is resetting `lastFrameMs` on resume; a real pause state (input gating, audio ducking, UI)
lands with the pause menu in Milestone 5.

## M0-13 — CI runs Playwright under xvfb with software WebGPU

GitHub's Linux runners have no GPU. Chromium's `--enable-unsafe-webgpu` with a software backend
keeps the real WebGPU path under test in CI instead of skipping it. Timing-based assertions are
therefore budget-free: the e2e suite asserts draw counts, sprite counts, tick progress and
recovery, never frame rate. Frame-rate budgets are measured on real hardware per the PRD's
performance test plan.

## M0-14 — Device loss is marked synchronously, before `device.lost` resolves

`device.lost` settles a microtask or more after the device actually dies. A frame submitted in
that window draws into a dead device: a validation error on a real driver, and a GPU-process
crash on Chromium's software backend, which is how CI found it. `RenderHost.markLost()` flips
the phase and un-builds every resource synchronously, so the render loop's `phase !== 'ready'`
guard is actually closed rather than nearly closed.

## M0-15 — The device-loss drill skips on software WebGPU adapters

Destroying the device kills Chromium's software backend outright, so on a GPU-less runner the
test measures SwiftShader, not our recovery path. The e2e test reads the adapter string and
skips with a stated reason when it matches a software backend; everywhere a real adapter exists
it stays strict. Verified on Apple Metal 3: recovery rebuilds every GPU resource and rendering
resumes. The rest of the WebGPU suite still runs in CI under software rendering.
